# Material Studio Constitution

## Core Principles

### I. 规格先行、需求可追踪

必须先将原题要求映射到 spec、契约、测试计划和任务，再编写对应业务实现。
原题 `docs/requirements-source.md` 为需求依据；新增假设和取舍必须显式记录。
规格、契约或状态模型变更必须先同步设计与任务，禁止静默扩大范围。

### II. TDD 不可跳过

每个业务行为必须遵循 RED → GREEN → REFACTOR：先写行为测试，实际运行并确认因缺少目标行为失败，
再最小实现，通过后重构并重跑相关测试。环境失败不算 RED；计划测试不算已执行。
后端必须覆盖阶段顺序、指定阶段失败中断；前端必须覆盖多任务隔离、查询异常与执行失败的区别。
文档及纯配置不强造无意义测试，但必须执行与其相符的格式、解析或构建验证。

### III. Java 拥有业务、持久化与异步执行

模板、素材、任务及历史业务由 Java/Spring Boot/MyBatis 提供，任务与状态保存至 MySQL。
提交仅完成校验和受理；后台独立执行素材检查 → 模拟生成 → 结果整理。
每一步必须可观察、可重复模拟失败，失败后不得执行后续阶段。查询不得推进状态，终态不得回退。
页面关闭不得取消已经受理的任务。

### IV. 用户与异步状态隔离

个人素材、任务及结果必须以当前用户身份校验归属，不能信任客户端传入 ownerId。
前端必须分别表达上传、提交、后台状态和查询错误，查询失败不得改写任务为 FAILED。
状态按用户和任务隔离；页面离开、用户切换及任务终结后必须清理相应订阅和请求。
旧请求不得覆盖新身份、其他任务或更新版本的状态。

### V. 简单且可复现的交付

必须提供锁定依赖、SQL 与种子、本地示例素材、CI、容器运行入口和诚实的 README。
应用安装、测试、构建与运行必须在容器中完成。CI 必须执行前端 lint/typecheck/test/build 及 Java test/package。
默认不使用真实 AI、消息队列、Redis 或额外身份服务；添加复杂度前必须说明需求与简单方案不足。

## 工程边界

前端必须使用 Next.js App Router、React、TypeScript；数据库必须使用 MySQL。
允许本地卷存储图片；不得仅保存浏览器临时地址。演示使用自制或合法公开素材。
不要求服务重启后自动续跑、真实生成、支付、复杂模板管理或第三方登录。
不得将规划中的实现或未运行的检查描述成已完成。

## 开发流程与质量门禁

严格单智能体串行开发，禁止委派或生成子智能体；技能中的并行研究由当前执行者逐项完成。
每个逻辑增量及时 Git 提交；需求、设计、实现分阶段保留可审阅历史。
实现前必须通过规格质量检查，按 tasks 中依赖顺序开发。
实现后必须记录 RED/GREEN 命令和结果、同步任务勾选和 README 完成状态。
交付前运行需求追踪和契约一致性审查；记录容器运行、CI 和人工验收各自结果及限制。

## Governance

本约章优先于仓库内通用开发模板；用户明确指令优先于本约章。
修改时必须更新版本、日期和 Sync Impact Report，并同步受影响的规格与计划。
删除或重新定义原则升级 MAJOR，新增原则升级 MINOR，澄清措辞升级 PATCH。
每次规划与交付必须逐条检查原则；例外必须在 plan 的 Complexity Tracking 中说明理由和替代方案。
